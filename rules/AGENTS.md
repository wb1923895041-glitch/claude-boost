# 工作准则（claude-boost）

- **够了就动手**：信息足够时直接做，不要重复推导已确认的事实，不要罗列不打算采用的方案。需要权衡时给出推荐，而不是穷举。
- **先读再改**：修改文件前先看它的现状和调用方；改动保持在用户要求的范围内，不顺手重构无关代码。
- **改完要验证**：改了代码就跑最小的相关验证（类型检查、构建、相关测试或实际运行一次），如实报告结果：失败就贴出失败输出，跳过了就说跳过了；确实验证通过了就直接说，不要含糊。
- **难以撤销的操作先确认**：删除数据、强推、改写历史、发布、部署、对外发消息，先向用户说明并等待明确同意；一次同意只对那一次有效。
- **出现 `[claude-boost]` 提醒时认真对待**：它报告的检查错误要先修掉；它指出你在重复失败时，换思路或向用户求助，不要原样重试。
- **密钥只放环境变量**：不要把 token、密码、私钥写进代码或提交进 git，用 `.env`（并确认已在 `.gitignore` 中）或环境变量读取。
- **可以撤销**：每次编辑前 claude-boost 都自动拍了快照。用户想撤销或回滚时使用 `rewind` 技能，不要凭记忆手动"改回去"。
- **记住重要的事**：用户纠正你的做法、说明偏好、给出项目背景时，使用 `memory` 技能记下来；新会话开头注入的记忆索引要留意。
- **审查要具体**：被要求 review 时使用 `code-review` 技能（涉及安全时用 `security-review`），只报能写出具体触发场景的问题。
- **提交走流程**：用户要求提交时使用 `commit` 技能；没被要求时不要自己提交或推送。
- **上下文太长就交接**：对话很长、你开始重复或遗忘前面的决定时，建议用户用 `handoff` 技能交接到新会话。
- **少调用、调用要大**（实测：编辑工具每次约 2 秒且多个编辑会排队串行；每次 run_command 有约 2 秒固定开销；读文件工具几乎 0 秒）：
  - 同一个文件的多处修改合并成**一次**编辑调用；新文件或大面积改动直接整文件写入。
  - 读文件、看目录、搜代码用对应的读取 / 搜索工具，不要用 `cat`、`Get-Content`、`Select-String`、`ls` 之类的命令。
  - 互不依赖的检查命令合并成一条（用 `;` 连接）一次跑完，而不是逐条运行。
- **汇报简洁**：结束时用两三句话说清现在是什么状态、改了什么、还有什么没做或没验证。不复述过程。
