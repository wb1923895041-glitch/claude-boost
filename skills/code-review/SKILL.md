# 代码审查

目标：找出**会导致错误行为、崩溃、数据丢失或安全问题**的缺陷，并逐条验证。宁可少报，不要误报。

## 1. 确定范围

- 默认：`git diff HEAD`（含已暂存和未暂存）+ `git status` 里的新文件。
- 用户指定分支：`git diff <base>...HEAD`；指定提交：`git show <sha>`；指定文件：直接读。
- 没有 git：审查用户点名的文件，或用 rewind 技能的 `list` 找本次会话改过的文件。

## 2. 读懂上下文

不要只看 diff。对每处改动，打开完整文件，并搜索被改函数的调用方和被调用方。很多 bug 出在改动和未改动代码的接缝处。

## 3. 逐项检查

按这个顺序过一遍，每一项都要真的去想：
- **正确性**：边界条件（空、0、负数、超长、并发）、off-by-one、错误的比较/逻辑运算、空值/undefined、异步未 await、异常被吞掉、资源未释放。
- **契约**：改了函数签名/返回值/数据格式，所有调用方都跟着改了吗？
- **状态**：缓存失效、重复执行、竞态、部分失败后的状态。
- **安全**：注入（SQL / 命令 / 路径穿越 / XSS）、未校验的用户输入、密钥硬编码、权限检查缺失。
- **数据**：迁移是否可逆、是否会误删、编码/时区问题。
- **测试**：改动的行为有没有被测试覆盖；已有测试是否因改动而失效却被"修"成了断言更弱的版本。

## 4. 验证每个疑点

对每个候选问题，写出**具体的触发场景**：什么输入/状态 → 得到什么错误结果。能跑就实际跑一下（最小复现脚本、相关测试）。写不出具体场景的，降级为"可能"或直接丢弃。

## 5. 输出

按严重程度排序，每条一行标题 + 简短说明：

```
1. [严重] path/to/file.ts:42 — 一句话描述缺陷
   触发：具体输入/步骤 → 错误结果
   修复建议：一句话
```

标注"已验证"（实际跑过）或"推断"。最后单独列 1–3 条值得做但不紧急的简化/清理建议（可选）。

没有发现问题就直说"没有发现会出错的问题"，不要为了凑数报风格问题。

**审查阶段不改代码**。列完后问用户要不要修；用户同意后再改，改完跑相关验证。
