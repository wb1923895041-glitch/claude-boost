# 安全审查

只报告**有现实攻击路径**的问题：说清楚攻击者从哪里输入什么、绕过什么、得到什么。理论风险和代码风格不报。

## 1. 范围与攻击面

- 范围：默认当前未提交改动（`git diff HEAD`）；用户要求时扩展到整个项目或指定模块。
- 先画出攻击面：哪些入口接收外部输入（HTTP 路由、表单、上传、Webhook、CLI 参数、消息队列、读取的文件/URL），谁能访问它们（匿名 / 登录用户 / 管理员）。

## 2. 逐类检查（从入口顺着数据流往下追）

| 类别 | 重点看 |
| --- | --- |
| 注入 | SQL 字符串拼接、ORM 的 raw 查询、`exec`/`spawn`/`os.system` 带 `shell=True` 拼接参数、模板注入、NoSQL 查询对象直接用请求体、LDAP/XPath |
| 跨站 | `innerHTML` / `dangerouslySetInnerHTML` / `v-html` / `|safe` 渲染用户内容；缺少 CSRF 防护的状态修改接口；开放重定向 |
| 鉴权与越权 | 接口缺少登录校验；用请求里的 `userId` 而不是会话里的身份查数据（IDOR）；只在前端做权限判断；JWT 未验签、接受 `alg: none`、密钥硬编码 |
| 文件与路径 | 用户可控的路径拼接（`../` 穿越）、上传未限制类型/大小、上传文件可被当作脚本执行、解压炸弹/zip slip |
| SSRF | 服务端按用户给的 URL 发请求，未禁止内网地址/云元数据地址 |
| 敏感信息 | 代码或配置里的密钥、日志里打印密码/token、错误信息向用户返回堆栈、`.env` 被提交 |
| 加密与会话 | 明文/弱哈希存密码（应 bcrypt/argon2）、`Math.random` 生成令牌、Cookie 缺 `HttpOnly`/`Secure`/`SameSite` |
| 反序列化 | `pickle.loads`、`yaml.load`（非 safe_load）、Java 原生反序列化处理不可信数据 |
| 配置 | CORS `*` 且允许凭据、调试模式上线、默认账号密码、过宽的云权限 |
| 依赖 | 有锁文件时运行 `npm audit --omit=dev` / `pnpm audit` / `pip-audit`（若已安装），只报告实际被用到且可达的高危漏洞 |

## 3. 验证

对每个疑点写出具体利用步骤（请求示例或输入示例 → 结果）。能在本地安全复现的（例如对本地开发服务器发一个请求、写一个单元测试）就复现；**不要对生产环境或第三方系统做任何测试**。写不出具体利用路径的丢弃。

## 4. 输出

```
1. [高危] src/api/user.ts:58 — 按请求参数 id 查询订单，未校验归属（IDOR）
   利用：登录用户 A 请求 GET /api/orders?id=<B 的订单号> → 返回 B 的订单详情
   修复：查询条件加上 userId = session.userId
```

按 高危 / 中危 / 低危 排序，标注"已复现"或"推断"。没有发现就直说。审查阶段不改代码，列完问用户要不要修。
